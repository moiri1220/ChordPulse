# ChordPulse 開発ロードマップ

本ロードマップは、MVPを小さく検証しながら、将来の精度向上・操作性向上へ段階的に進めるための指標である。各Phaseの完了条件を満たした時点で次のPhaseへ進む。

## Phase 1：コアエンジンの検証（ローカル環境 / CLI）

### 実施内容

- Python実行環境と解析依存関係を固定する。
- `yt-dlp`等によるYouTube音声取得を、利用規約・APIポリシー・権利条件を確認した範囲で検証する。条件を満たせない場合は機能を無効化する。
- MP3/WAVと取得済みWAVを入力に、`librosa`でBPM・拍位置を推定する。
- コード認識の交換インターフェースとクロマテンプレートによるベースラインを実装し、Chordinoまたは`madmom`へ差し替えられる状態にする。
- 拍・小節・コード区間を統合する内部データ形式を定義する。
- `music21`でシンプルなコードネーム付きMusicXMLを生成する。
- 代表的なテスト音源で、解析結果とMusicXMLを目視確認する。

### 完了条件

- ローカル音源からMusicXMLを再現性をもって生成できる。
- ローカル音源と、利用条件を確認したYouTube URLでパイプラインを実行できる。違法アップロードと知りながらの取得や制限回避は行わない。
- BPM、拍、小節、コードが後続処理へ渡せる形式で保存される。
- 生成MusicXMLを一般的なMusicXMLビューアまたはOSMDで開ける。

## Phase 2：バックエンドAPIと描画プロトタイプ（MVP）

### 実施内容

- FastAPIで`POST /analyze`を実装する。
- ファイル入力と、設定で有効化されたYouTube URL入力を受け付ける。
- 利用条件確認への同意を検証し、違法入手と知りながらの入力や利用条件に反する入力を音源取得前に拒否する。
- 音源を解析中だけ一時保持し、解析完了後または失敗時に削除する。
- `rhythm_level`を受け取り、レベル1〜3のMusicXML生成へ渡す。
- フロントエンドで解析フォーム、処理状態、エラー状態を実装する。
- OpenSheetMusicDisplay（OSMD）を組み込み、生成MusicXMLをブラウザ描画する。
- 推定BPMを結果画面に表示する。
- MusicXMLダウンロードボタンを実装する。

### 完了条件

- ブラウザから入力して解析を完了できる。
- レスポンスのMusicXMLがOSMDで表示される。
- レベル1〜3の違いを生成譜面で確認できる。
- 成功・入力エラー・解析エラーの状態が画面で判別できる。
- 利用条件に反する音源、違法入手と知りながらの入力、設定で無効化されたYouTube URLが処理されない。

## Phase 3：リズム指定機能とUIの洗練

### 実施内容

- リズムレベルの切替UIと説明を改善する。
- `librosa`のOnset検出をレベル3へ組み込み、8分音符の打ち分けとシンコペーションを調整する。
- コード区間の量子化・隣接コード統合・未判定区間の扱いを改善する。
- 解析中の進捗、処理時間、再試行導線を改善する。
- 譜面の見やすさ、レスポンシブ表示、ダウンロード導線を調整する。
- 元音源と譜面の同期再生に向けた技術検証を行う。

### 完了条件

- レベルごとの目的と出力差が利用者に伝わる。
- 代表的なリズムパターンで、レベル3の出力がレベル2より情報量のある譜面になる。
- 解析失敗やコード未判定があっても、利用者が状態を理解できる。

## Phase 4：精度強化とモデル拡張（将来アップデート）

### 実施内容

- コード解析エンジンを比較評価し、楽曲ジャンル別の精度を測定する。
- アタック・音符検出にBasic PitchなどのAIモデルを導入し、既存のOnset検出とハイブリッド化する。
- 転調、複雑なコード、拍子推定などの対応範囲を拡張する。
- 解析処理を非同期タスク化し、Celeryなどを利用したジョブ実行へ移行する。
- キャッシュ、キュー、処理時間上限、リソース制御を導入する。
- 必要に応じて、譜面の手動編集、音源同期再生、保存・共有機能を検討する。
- YouTube機能は、現行のYouTube規約・APIポリシー・取得方法を継続確認し、条件に適合しなくなった場合は設定で無効化する。

### 完了条件

- 評価用データセットに基づく精度指標を継続的に比較できる。
- 長時間音源や同時リクエストを想定した処理方式へ移行できる。
- 新しい解析モデルを既存APIやMusicXML生成処理へ影響を限定して追加できる。

## 推奨する実装順序

```text
Phase 1
  -> 内部解析データ形式の確定
  -> MusicXML生成の安定化
Phase 2
  -> API契約の確定
  -> OSMD表示とダウンロード
Phase 3
  -> リズム表現の改善
  -> UI/UX改善
Phase 4
  -> 精度評価とAIモデル
  -> 非同期処理・機能拡張
```
